## Message search pagination — design requested 2026-10-21

The [design and acceptance matrix](docs/SEARCH-PAGINATION.md) define the complete behavior. The subsequent owner implementation request authorizes application changes and synthetic verification; live mailbox access remains a separate opt-in.

Design deliverables:

- [x] Review current contracts, adapter, MCP boundary, tests, and safety requirements.
- [x] Specify cursor format, query binding, process lifetime, errors, compatibility, and behavior under mailbox changes.
- [x] Define implementation sequence and unit/protocol/MCP/live acceptance requirements.

Implementation sequence — authorized 2026-10-21:

1. **Contracts and cursor codec.** Add optional `Cursor` to `SearchRequest`, nullable `NextCursor` to `SearchResult`, and a small internal versioned HMAC codec with a per-process key. Preserve `IReadOnlyMailbox`'s three methods. Test observable round trips, exact binding/null/INBOX rules, tampering, length/encoding bounds, restart invalidation, and integer boundaries. No persisted cursor state or new package/configuration.
2. **Read-only adapter.** Validate cursors before I/O, enforce both folder-policy checks and resolved-name identity, check UIDVALIDITY before continuation search, and apply a typed finite UID range. Advance from the lowest selected candidate even if summaries vanish; preserve ordering, caps, truncated/cursor equivalence, cancellation, deadline, and cleanup. Verify pinned MailKit 4.18.1 range APIs and actual wire commands without expanding the numeric UID range into a list.
3. **Protocol regressions.** Use the real adapter and scripted TLS/IMAP sessions to traverse more than 50 synthetic matches, exercise sparse/extreme UIDs, arrivals/removals/flag changes, empty/final pages, stale epochs, denied folders, invalid server responses, cancellation and recovery. Admit only expected read/session commands, with at most 50 summary candidates fetched per page. Existing get_message PEEK coverage must remain passing.
4. **MCP integration.** Map the new argument/result, set strict schema bounds, and describe repeated filters, terminal cursors, process lifetime, and empty-page behavior. Add SDK process tests for full traversal, backward-compatible first-page requests, output equivalence, sanitized errors/logging, and exactly three tools.
5. **Documentation and synthetic completion.** Update DESIGN, SECURITY, USAGE, TESTING, backlog/status references, and this ledger to match implemented behavior. Review CONFIGURATION and DEVELOPMENT; no configuration or launch change is expected. Run locked restore, Release build, and the full non-live suite using [the development commands](docs/DEVELOPMENT.md#build-and-test-workflow). Record actual outcomes and environmental limits; run `git diff --check` and Markdown link/fence/JSON checks.
6. **Gated Bridge acceptance.** Extend the existing opt-in read stage to walk the operator-prepared folder with page size 1 and compare the known manifest and persistent flags before/after. Test the gate synthetically. Execute live only with separate explicit authorization and external configuration; retain 2–50 fixture messages and the single-folder allowlist. Record tested versions and limitations, without mailbox values.

## Security and privacy review — 2026-10-18

Findings and remaining work:

- **Resolved by the remediation recorded below.** At review time, configuration and certificate integrity was not enforced by the loader: both used ordinary `File.OpenRead`, whereas the password used opened-handle ownership/mode validation. A synthetic startup check with mode `0666` configuration/certificate files and a private `0600` password succeeded (exit 0, empty stdout/stderr, no mailbox calls). This proved unsafe modes were accepted, not a completed cross-user attack. If another local user could modify the reachable configuration, they could change the endpoint and pin before restart to receive credentials at their own loopback service or broaden the allowlist. Private placement mitigated this pending the implementation fix.
- Search materializes all matching UIDs before limiting output; ENVELOPE/BODYSTRUCTURE parsing precedes metadata caps. Large mailboxes or hostile message metadata can consume resources outside the body-transfer cap. This is already a documented design limitation; no resource-exhaustion exploit was demonstrated. Review metadata/response budgets and add adversarial protocol fixtures before claiming comprehensive memory bounds.
- Plaintext tool results leave the process for the trusted MCP client. Hosted-model disclosure, client retention, downstream prompt injection, process memory/swap/dumps, and write-capable Bridge credentials remain trust-model risks. Read-only annotations and HTML conversion do not remove those risks.
- Full live flag/membership preservation and Bridge failure/recovery evidence remain pending. Dependency pins/audit policy were inspected, but fresh advisory feeds and installed runtime vulnerabilities were not audited during this review.
